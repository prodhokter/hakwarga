# Starline Design System

**Version 2.4.0** — Enterprise Dashboard & POS Platform

## Overview

Starline is a modern glassmorphism business management dashboard system built for POS, payroll, and accounting software. It serves professionals who manage daily operations at scale — retail managers tracking inventory, accountants reconciling ledgers, and HR teams processing payroll. The interface communicates clarity, speed, and reliability through translucent frosted surfaces, a luminous lime-yellow brand accent, and a calm slate-gray secondary palette.

The emotional response Starline aims for is *controlled urgency* — the confidence of a well-organized back office paired with the energy of a bustling retail floor. The lime-yellow accent (`{colors.primary}`) acts as a visual anchor for primary actions, glowing against translucent glass panels (`{colors.surface}`) that layer information without visual weight. This is a dashboard that feels fast before you click anything.


## Colors

### Brand & Accent

Starline's brand is anchored by a singular luminous accent: **Lime-Yellow** (`{colors.primary}`). It appears exclusively on interactive elements that demand attention — primary CTAs, active states, selected indicators, and brand moments. Unlike traditional enterprise dashboards that use blue or green, lime-yellow injects energy into business software without sacrificing professionalism. The accent is paired with **Slate** (`{colors.secondary}`) as a neutral secondary for non-primary actions such as cancel buttons, secondary filters, and toolbars.

The on-colors are carefully tuned: `{colors.on-primary}` (`#1e293b`) provides maximum contrast against the lime-yellow background, while `{colors.on-secondary}` (`#ffffff`) keeps text crisp on slate surfaces. In dark mode, both on-colors shift to near-black (`{colors-dark.on-primary}` `#0f172a`) to maintain readability against the same brand-consistent primary.

### Surface

Starline's defining visual feature is its **glassmorphism surface hierarchy**. The page background (`{colors.background}`) is a soft blue-gray tone that provides a cool, clean canvas. On top of this, translucent white surfaces (`{colors.surface}` at 70% opacity) create a frosted-glass effect with subtle backdrop blur. This allows layered information to remain distinct without heavy borders or shadows.

### Semantic

Semantic colors follow a consistent pattern: each has a base, hover, active, background, subtle, and muted variant (stored in CSS variables but not in the core token set). The primary semantic tokens are:

- **Success** (`{colors.badge-success}` `#22c55e` → dark `#4ade80`) — approved transactions, completed payroll runs, active inventory
- **Warning** (`{colors.badge-warning}` `#f59e0b` → dark `#fbbf24`) — pending approvals, low-stock alerts, expiring records
- **Danger** (`#ef4444` → dark `#f87171`) — failed transactions, declined payments, error states
- **Info** (`{colors.badge-info}` `#3b82f6` → dark `#60a5fa`) — system notifications, sync status, informational banners
- **Link** (`{colors.link}` `#3b82f6` → dark `#60a5fa`) — hyperlinks, navigation cues
- **Ring Focus** (`{colors.ring-focus}`) — keyboard focus indicators, active input outlines

## Typography

### Font Family

Starline uses **Geist** as its primary typeface — a geometric sans-serif designed for modern UI density. Geist combines the clarity of Inter with tighter letterforms optimized for dashboard interfaces where information density is high. The font stack is:

```
--font-display: 'Geist', system-ui, -apple-system, sans-serif;
--font-body: 'Geist', system-ui, -apple-system, sans-serif;
--font-mono: 'Geist Mono', ui-monospace, monospace;
```

Geist serves as both display and body typeface, providing a unified typographic voice. Geist Mono is reserved for code blocks, financial figures, tabular data, and system output.

### Principles

1. **The Tight Display Rule** — Display-level typography uses negative letter-spacing (`-0.03em` to `-0.025em`) to create dense, impactful headlines that read quickly — critical for dashboard KPIs and metric cards where space is premium.

2. **The Unified Weight Rule** — Starline restricts itself to two font weights: 400 (normal) for body copy and 600 (semibold) for headings and buttons. Bold (700) is reserved exclusively for display-level hero text. This creates a clean, consistent typographic voice without visual noise.

3. **The Mono Figure Rule** — All financial figures, transaction amounts, payroll numbers, and tabular data use `{typography.code-md}` or `{typography.code-sm}` — even within otherwise proportional body text. This ensures numbers align vertically for rapid scanning.

### Note on Font Substitutes

When Geist is unavailable (e.g., third-party environments, email clients, offline fallbacks), the stack degrades to `system-ui, -apple-system, sans-serif`. System-ui matches Geist's geometric proportions more closely than generic sans-serif. For Geist Mono, the fallback is `ui-monospace, monospace` — monospace system fonts that preserve column alignment for financial data.

## Layout & Spacing

### Spacing Scale

Starline uses a base-4 grid system derived from a numerical spacing scale (0.25rem increments). Semantic keys map to specific points on this scale for consistent application:

| Token | Value | Rem | Usage |
|-------|-------|-----|-------|
| `{spacing.xxs}` | 0.125rem | 2px | Hairlines, icon gaps, dense table cell padding |
| `{spacing.xs}` | 0.25rem | 4px | Micro spacing, badge padding, compact elements |
| `{spacing.sm}` | 0.5rem | 8px | Tight spacing, button padding, form gaps |
| `{spacing.md}` | 0.75rem | 12px | Default spacing, input padding, chip margins |
| `{spacing.lg}` | 1rem | 16px | Card inset, section internal padding |
| `{spacing.xl}` | 1.5rem | 24px | Card padding, panel gutters, modal padding |
| `{spacing.xxl}` | 2rem | 32px | Section internal spacing, sidebar padding |
| `{spacing.xxxl}` | 3rem | 48px | Feature spacing, large card groups |
| `{spacing.section}` | 6rem | 96px | Between major sections, page padding |
| `{spacing.band}` | 10rem | 160px | Maximum separation, hero bands |
| `{spacing.safe-area}` | `env(safe-area-inset-bottom, 0px)` | dynamic | Bottom padding for fixed bottom nav on notched/gesture-bar devices |

### Grid

Starline follows a 12-column responsive grid with 24px column gutters (`{spacing.xl}`). Content containers max out at 1280px with 24px outer padding. For dashboard layouts specifically, narrower grids (8-column or 4-column) are preferred to keep data cards compact and scannable.

### Whitespace Philosophy

Dashboard interfaces face a fundamental tension: information density vs. readability. Starline resolves this with **translucent whitespace** — the glassmorphism surfaces (see Surfaces above) create visual separation between content groups without requiring large empty margins. The card surface (`{colors.surface-card}`) at 70% opacity provides enough distinction that 16px internal padding (`{spacing.lg}`) replaces the 24-32px padding traditional dashboards require. This allows Starline to fit more data on screen without feeling cluttered.

## Elevation & Depth

### Level Table

Starline uses a 5-level elevation system that combines CSS box-shadows with the inherent depth of glassmorphism surfaces. Levels 1-3 are ideal for interactive and container elements, while levels 4-5 handle overlapping components.

| Level | Light Treatment | Dark Treatment | Use Case |
|-------|----------------|---------------|----------|
| 0 | `none` | `none` | Page background, flat text blocks, table rows |
| 1 | `0 1px 3px rgba(0,0,0,0.05)` | `0 1px 3px rgba(0,0,0,0.3)` | Cards, small widgets, form inputs |
| 2 | `0 4px 12px rgba(0,0,0,0.08)` | `0 4px 12px rgba(0,0,0,0.4)` | Dropdown menus, popovers, hovered cards |
| 3 | `0 8px 24px rgba(0,0,0,0.1)` | `0 8px 24px rgba(0,0,0,0.5)` | Modals, side panels, date pickers |
| 4 | `0 20px 50px rgba(0,0,0,0.05)` | `0 20px 50px rgba(0,0,0,0.4)` | Hero bands, large splash sections |

### Decorative Depth

Beyond system shadows, Starline uses three visual depth techniques:

- **The Frosted Glass Layer** — Surfaces at 70% opacity with backdrop blur (`{colors.surface}`) sit above the background canvas, creating the illusion of physical glass panels without shadow. This is the primary depth mechanism for cards and panels.
- **Hero Gradient Glow** — The `{colors.hero-warm}` to `{colors.hero-glow}` gradient provides atmospheric depth on hero sections, login screens, and metric backgrounds. In dark mode, `{colors-dark.hero-pink}` (`#fca5a5`) adds a warm counterpoint to cool dark backgrounds.
- **Dark Band Inversion** — In dark mode, surfaces use the opposite depth logic: `{colors-dark.surface-card}` is lighter (`rgba(30,41,59,0.7)`) than `{colors-dark.background}` (`#0f172a`), creating an inverse pyramid where cards lift *forward* from the dark canvas rather than receding into it.

## Shapes

### Border Radius Scale

Starline's shape language combines generous rounding for interactive elements with tighter corners for data-dense containers. Most radii are derived from the base-4 grid.

| Token | Value | Usage |
|-------|-------|-------|
| `{rounded.none}` | 0 | Hero bands, full-bleed sections, table headers |
| `{rounded.xs}` | 0.125rem (2px) | Checkbox corners, inline tags, dense table elements |
| `{rounded.sm}` | 0.5rem (8px) | Text inputs, textareas, selects, alerts, progress bars |
| `{rounded.md}` | 0.75rem (12px) | Toasts, notification panels, compound inputs |
| `{rounded.lg}` | 1rem (16px) | Cards, modals, side panels, elevated containers |
| `{rounded.full}` | 9999px | Buttons (pill), badges, tabs, switches, avatars |

The shape of each component is defined by a dedicated `--shape-*` token:

| Component | Shape Token | Effective Radius |
|-----------|-----------|-----------------|
| Button | `pill` | `{rounded.full}` |
| Input | `rounded` | `{rounded.sm}` |
| Card | `2xl` (1.5rem) | `{rounded.lg}` |
| Badge | `full` | `{rounded.full}` |
| Modal | `2xl` (1.5rem) | `{rounded.lg}` |
| Avatar | `full` | `{rounded.full}` |
| Tabs | `full` | `{rounded.full}` |
| Switch | `pill` | `{rounded.full}` |
| Progress | `rounded` | `{rounded.sm}` |
| Alert | `rounded` | `{rounded.sm}` |

### Photography Geometry

For dashboard interfaces, imagery is primarily functional rather than decorative:

- **POS Product Images** — Square (1:1 aspect ratio), `{rounded.sm}` corners, rendered within cards at 64-80px. Full-bleed within the image container.
- **Employee/User Avatars** — Circular (via `{rounded.full}`), 40px default, 64px for detail views. Always inside a transparent container — no background fill.
- **Hero Section Graphics** — 16:9 aspect ratio, full-bleed, no border radius. Treated as atmospheric covers with the `{colors.hero-warm}` overlay gradient.
- **Report/Chart Thumbnails** — 4:3 aspect ratio, `{rounded.sm}` corners, embedded inside cards with 8px padding from the card edge.

## Do's and Don'ts

### Do

- :white_check_mark: **Use `{colors.primary}` sparingly** — lime-yellow is the singular brand accent. Reserve it for primary CTAs, active states, and critical indicators only. Overuse dilutes its signaling power.
- :white_check_mark: **Apply glassmorphism surfaces (`{colors.surface}`) for all elevated containers** — the 70% opacity frosted effect is Starline's defining visual. Cards, modals, panels, and dropdowns should use translucent backgrounds.
- :white_check_mark: **Use `{typography.button-md}` for primary actions** — the semibold weight at 16px with line-height 1.0 creates compact, readable buttons that fit dashboard density.
- :white_check_mark: **Format all financial figures in `{typography.code-md}` or `{typography.code-sm}`** — mono-spaced numbers align vertically for rapid comparison across rows.
- :white_check_mark: **Use `{rounded.full}` for buttons, badges, and tabs** — pill-shaped interactive elements create a modern, approachable feel for enterprise software.
- :white_check_mark: **Apply `{spacing.xl}` (24px) for card internal padding** — the glass surface provides enough visual separation that 24px feels generous without wasting space.
- :white_check_mark: **Use the dark mode surface hierarchy inversely** — in dark mode, surfaces should be lighter than the background (e.g., `{colors-dark.surface-card}` at 70% opacity on `{colors-dark.background}` `#0f172a`).
- :white_check_mark: **Reference design tokens directly** — use `{colors.primary}`, `{typography.body-md}`, `{rounded.lg}` consistently across all code and documentation.

### Don't

- :x: **Don't apply `{colors.primary}` to large background areas** — lime-yellow is an accent, not a surface color. Full-page yellow backgrounds overwhelm and dilute the accent's impact.
- :x: **Don't use opaque white surfaces** — the glass effect requires transparency. Always use `{colors.surface}` (70% opacity) or `{colors.surface-card}` rather than pure `#ffffff`.
- :x: **Don't introduce additional accent colors** — the system has one brand accent (`{colors.primary}`), one secondary (`{colors.secondary}`), and four semantic colors. Any new color breaks the visual hierarchy.
- :x: **Don't use heavy shadows on frosted glass surfaces** — the glass itself provides depth. Level 1 elevation (`0 1px 3px rgba(0,0,0,0.05)`) is sufficient for most glass containers.
- :x: **Don't override the pill shape on buttons** — buttons must use `{rounded.full}`. Any deviation from pill-shaped buttons breaks the interactive shape language.
- :x: **Don't use thin font weights (300 or lower) for any UI text** — minimum 400 (normal) for body, 600 (semibold) for headings. Thin text reduces readability on dashboard screens.
- :x: **Don't place text directly on background without a surface** — always use a card, panel, or surface container. Text on `{colors.background}` lacks the glass layer's definition.
- :x: **Don't ignore dark mode** — both light and dark variants are defined for every color token. Test all UI in both modes before shipping.

## Responsive Behavior

### Breakpoints

| Name | Width | Key Changes |
|------|-------|-------------|
| Mobile | < 640px | Single-column layout, bottom navigation, full-width cards, collapsed sidebar |
| Tablet | 640px - 1023px | 2-column grid, condensed sidebar (icons only), reduced card padding to `{spacing.lg}` |
| Desktop | 1024px - 1279px | 3-column grid, expanded sidebar, full card padding `{spacing.xl}` |
| Wide | 1280px+ | 4-column grid, max content width 1280px, additional whitespace |

### Touch Targets

All interactive elements maintain a minimum 44px touch target on mobile devices. This affects:

- **Small buttons** (`{component.button-sm}`) — height increases from 36px to 44px on mobile, maintaining the same visual padding via increased internal spacing.
- **Dropdown items** (`{component.dropdown-item}`) — height increases from 36px to 44px on mobile.
- **Tab items** — height stays 36px but internal padding increases to maintain 44px tap area via transparent extension.
- **Table rows** — maintain minimum 44px row height on mobile, regardless of content density.

### Collapsing Strategy

- **Sidebar** (`{component.sidebar}`) — collapses to icon-only rail (60px) on tablet, hidden behind hamburger on mobile. The navigation becomes a bottom tab bar on mobile with 5 primary destinations.
- **Bottom tab bar** — fixed to the bottom edge and must apply `{spacing.safe-area}` (`env(safe-area-inset-bottom)`) as bottom padding so items clear the iOS home indicator / Android gesture bar.
- **Cards** — on mobile, cards switch from inline grid to stacked vertical layout. Padding reduces from `{spacing.xl}` (24px) to `{spacing.lg}` (16px).
- **Tables** — on mobile, horizontal scroll is enabled with sticky first column. Alternatively, tables convert to stacked card layout where each row becomes a mini-card.
- **Modals** — on mobile, modals become full-screen sheets with `{rounded.none}` top corners and full-width bottom edge.
- **Navbar** (`{component.navbar}`) — height reduces from 60px to 56px on mobile. Logo and primary actions remain, secondary navigation moves to the bottom tab bar.

### Image Behavior

- **Product/Item images** — serve at 1x (standard) and 2x (Retina) resolution. On mobile, images render at 80px square; on desktop, at 64px within table rows and 120px within card layouts.
- **Hero graphics** — use CSS gradient fallbacks before loading heavy image assets. The `{colors.hero-warm}` to `{colors.hero-glow}` gradient serves as the base, with imagery layered on top.
- **Avatar images** — always circular (`{rounded.full}`) via `object-fit: cover`. Serve at 40px for default, 64px for detail views. DPR-aware via `srcset`.
- **Chart/report previews** — use SVG-based rendering that scales proportionally regardless of viewport. Never use raster images for chart previews.

## Iteration Guide

1. **Focus on one component at a time.** When adding or modifying a component, start with its token references (`{colors.primary}`, `{typography.button-md}`) and spec format (background, text, type, rounded, padding, height). Do not change multiple components simultaneously.

2. **Reference tokens directly, never hardcode values.** Every color, spacing, radius, and typography value in code must reference the corresponding CSS variable (`var(--palette-primary)`), not raw hex/px values. If a token doesn't exist for a needed value, add it to `design-token.json` first.

3. **Run validation after every edit.** Use the theme validation checklist to verify: correct file count, v2.4.0 versioning, Style Dictionary schema conformance (value + type only, no `$` prefix), and dark mode parity for all color tokens.

4. **Add new variants as separate component entries.** If a new button size is needed (e.g., `button-lg`), create a new entry in the components YAML with all 5 spec properties. Never modify an existing component token to suit a new use case.

5. **Keep the brand accent scarce.** When adding new UI elements, ask: "Does this need `{colors.primary}`, or can it use `{colors.secondary}` or a surface color?" Reserve lime-yellow for the single most important action per view.

6. **Dark mode must mirror light mode tokens exactly.** Every `colors` token must have a `colors-dark` counterpart. When adding a new color, add both light and dark values. Use the CSS dark selector block (`[data-theme="dark"]`) consistently.

7. **Test at all responsive breakpoints.** After any layout change, verify at mobile (< 640px), tablet (640-1023px), desktop (1024-1279px), and wide (1280px+) breakpoints. Ensure touch targets meet 44px minimum on mobile.

8. **Document new tokens in this document.** When a new token is added to `design-token.json`, update the YAML front matter and relevant prose section of this file. Token documentation and code must stay synchronized.

9. **Use glassmorphism intentionally.** Not every container needs frosted glass. Use `{colors.surface}` for interactive/raised elements and `{colors.background}` for static page areas. Deep layers (footer, secondary panels) use `{colors.surface-deep}`.

10. **Maintain the single-accent discipline.** If the design requires a second accent color beyond the semantic set (success, warning, danger, info), escalate to the design system lead. Additional accent colors must be approved before implementation.

## Known Gaps

- **Loading & Skeleton States** — Component-level loading skeletons and shimmer animations are not yet defined as design tokens. Skeleton colors, animation timing (`{animation.duration}`), and layout patterns are pending.
- **Focus-Only Variants** — Several components (checkbox, radio, switch) rely on `{colors.ring-focus}` for keyboard focus but lack documented pressed/active variants. These should follow the same pattern as text input focus styles.
- **Drag & Drop States** — Dragged item elevation (currently using Level 5 shadow) and drop-zone indicators (dashed border pattern, colors) are not formally tokenized.
- **Empty States** — No design tokens exist for empty-state illustrations, messaging typography, or CTA placement within empty containers.
- **Page-Level Layouts** — The main dashboard layout (sidebar + navbar + content area proportions), login page, and settings page layouts are not extracted into design tokens. These exist only in implementation.
- **Data Visualization Tokens** — Chart colors, axis label typography, grid line colors, and legend spacing are not defined. Financial dashboards rely on ad-hoc chart configurations.
- **Print Styles** — Payroll reports, invoice PDFs, and receipt print layouts are not covered by the token system. Print-specific typography (smaller sizes, different fonts) and monochrome color mapping are missing.
- **Reduced Motion** — `prefers-reduced-motion` media query handling and static fallback durations for `{animation.duration}` tokens are not documented.
- **High Contrast Mode** — Windows High Contrast Mode and forced-colors media query adjustments are not defined in the token system.
- **Third-Party Environment Fallbacks** — CSS variable resolution strategies for environments that strip `var()` (email clients, iframe embeds, legacy browsers) are not documented. The `{typography.fontFamily}` fallback stack covers font substitution, but color fallbacks are incomplete.
